# Turn Engine And Command Dispatch

Version: 1.0.0

## Overview

The turn engine converts player intent, internally queued upkeep commands, and
monster actions into time progression. It must preserve the distinction between
player-entered commands and forced turns so paralysis, knockout, command mode,
and invalid commands cannot create free actions or no-energy loops.

## Dependencies

This spec depends on [UBIQUITOUS_LANGUAGE.md] for command, command mode, turn,
energy, and moral-access terms. It depends on [parameters.md] for movement
energy, queue capacity, speed conversion, and timed-effect limits. It is used by
the core engine, player, monsters-combat, frontends-ui, save-load, and
test-system specs.

## Parameters

- Full movement energy: forced sleep, waiting, ordinary movement, stairs, many
  object uses, and valid monster orders consume one full action. Rationale: these
  actions advance world time and must let monsters act.
- Zero energy: invalid commands, canceled prompts, unavailable actions, and
  display-only commands consume no action energy. Rationale: the player must not
  be punished for failed UI or invalid intent.
- Queue capacity: queued commands are bounded. Rationale: auto-repeat,
  background pathing, command mode, and UI input must not grow memory or loop
  indefinitely.
- Speed energy: player and monster energy gain per world tick comes from the
  shared speed conversion. Rationale: initiative must be consistent for all
  actors.
- Paralysis and knockout duration: paralysis is a timed effect whose forced
  turns continue until the effect expires. Rationale: incapacitation must advance
  danger instead of waiting for new player intent.
- Commanded-monster timeout: command control over a monster is time-limited.
  Rationale: commanded allies must not become permanent player extensions.

## Data Structures

- Queued command: an engine command with context, command code, repeat count,
  background status, and typed arguments.
- Player intent command: a queued command originating from keyboard, mouse,
  menu, macro, repeat, or test-front-end input.
- Forced upkeep command: a queued command inserted by the engine to spend a
  player turn for paralysis, knockout, sleep, rest, or similar upkeep.
- Background command: a queued command generated by an automated pathing,
  repeated, or helper flow rather than direct immediate player input.
- Command context: the current domain in which a command is valid, such as
  gameplay or birth.
- Energy use field: the amount of player energy consumed by the command most
  recently processed.
- Last repeatable command: the most recent non-background command eligible for
  repeat.
- Commanded monster: the monster currently accepting player orders through
  command mode.

## Behavior

- The engine MUST process queued commands in order until a command spends energy
  or the queue becomes empty.
- A command that spends energy MUST end the current player-command processing
  slice and allow cleanup, monster processing, and world time to continue.
- A command that spends no energy MAY be followed by another queued command in
  the same processing slice.
- Player energy MUST be reduced by the command's energy use during player
  cleanup, not merely because a command was queued.
- Full-turn commands MUST add the spent energy to total player energy accounting.
- Forced upkeep commands MUST remain semantically distinct from player intent
  commands even when they share the same command queue.
- When the player is paralyzed or knocked out, the engine MUST queue or execute a
  forced upkeep turn and that turn MUST consume full movement energy.
- Forced sleep or upkeep commands MUST NOT be remapped into command-mode monster
  orders.
- Command mode remapping MUST apply to player command intent while a commanded
  monster is active.
- During command mode, ordinary player intent SHOULD be interpreted as a monster
  order when valid for command mode.
- During command mode, invalid monster orders MUST report valid command choices,
  consume no energy, and leave forced upkeep commands unmasked.
- Command mode MUST be releasable by a valid player intent command.
- A commanded monster that is held or commanded MUST miss its own normal monster
  turn while under that control effect.
- Command-control expiration MUST release the commanded monster and clean up the
  player command state.
- Background commands MUST NOT become the last repeatable player command unless
  explicitly allowed.
- Repeated commands MUST count down only when the command actually executes as
  the repeated action.
- Auto-repeat MAY enqueue further movement, pathing, or interaction commands, but
  each game-affecting step MUST still spend appropriate energy.
- Bloodlust or other coercive timed effects MUST only redirect commands that can
  spend energy and are not exempt background upkeep.
- A canceled command that set up a tentative coercion skip MUST be reconciled
  during cleanup based on whether energy was actually spent.
- The engine MUST disturb, flush, or cancel commands when world events make the
  queued intent stale.
- Front ends MUST treat a repeated unchanged acknowledgement prompt with
  unchanged energy as a possible no-energy command loop and not as ordinary input
  lag.
- Tests MUST cover the interaction of command mode, forced sleep, paralysis or
  knockout, invalid monster commands, and energy use.

## Error Handling

- If a queued command code is unknown for the current command table, processing
  MUST ignore it without spending energy.
- If a command is invalid in its context, it MUST fail without corrupting the
  command queue or spending energy.
- If the queue is full, enqueue MUST fail cleanly and preserve existing command
  order.
- If command mode has no commanded monster, monster-order commands MUST fail
  without spending energy.
- If forced paralysis or knockout repeatedly shows the same acknowledgement
  prompt while player energy remains unchanged, that is a turn-engine regression.
- If a command prompt requests more input and the player cancels it, cleanup MUST
  leave repeat and coercion state consistent with zero energy use.

## Implementation Notes

Command dispatch may use shared queue infrastructure for UI intent, repeats,
background helpers, and forced upkeep. The critical invariant is carried by
command semantics: internal upkeep commands are not player orders. Fixes should
therefore preserve compatibility of command identifiers while making the
remapping rule explicit.

Avoid solving command-mode bugs in the terminal layer. The terminal can reveal a
loop, but energy accounting and forced-turn semantics belong to gameplay.

## Test Scenarios

- Command-mode forced sleep: create a commanded player state, queue a forced
  sleep turn, process one gameplay command, and verify full movement energy was
  spent.
- Paralysis forced turn: apply paralysis while command mode is active, process
  the next player slice, and verify the player loses a turn rather than issuing a
  monster order.
- Knockout forced turn: apply the knockout grade of stunning, process forced
  upkeep, and verify energy is spent until the incapacitating state recovers.
- Invalid commanded-monster action: enter command mode, issue an invalid monster
  order, verify the valid-command message appears, verify no energy is spent, and
  then verify a later forced sleep command still spends energy.
- Release command mode: enter command mode, issue the release command, verify the
  monster is no longer commanded and normal player intent resumes.
- Background pathing command: trigger pathing that enqueues background open or
  tunnel steps and verify each game-affecting step spends energy without
  replacing the last repeatable direct command.
- Repeat command: repeat a valid energy-using command and verify repeat count
  decrements only after execution.
- Cancellation: open a prompt-backed command, cancel it, and verify no energy is
  spent and the next eligible command is not incorrectly coerced.
- Terminal prompt recovery: reproduce a repeated unchanged acknowledgement prompt
  and verify diagnostics include player energy before and after acknowledgement.
